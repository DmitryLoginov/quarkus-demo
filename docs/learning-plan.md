# Quarkus: учебный CRUD с PostgreSQL

## Цель и порядок работы

Ты реализуешь REST API каталога книг и учишься объяснять его устройство через знакомые концепции Spring Boot. Ассистент выдаёт задания и делает ревью; исходный код и тесты пишешь ты. Ниже — маршрут и ТЗ, а не готовые решения. Текущий этап и история ревью находятся в [AGENTS.md](../AGENTS.md).

Каждая итерация: теория и чтение → реализация → проверка → ревью → исправления → контрольная точка. Дальние этапы задают ориентир; перед их началом наставник уточняет задание с учётом уже написанного кода.

## Выбор подхода

- **Hibernate ORM + Panache Repository — основной вариант.** Явный репозиторий позволит сравнить подход со Spring Data JPA, сохранив знакомые сущности и транзакции.
- Panache Active Record — компактнее, но операции хранения располагаются на самой сущности; сравним после освоения Repository.
- Hibernate Reactive — отдельная тема с другой моделью выполнения; для первого CRUD выбираем синхронные методы и JDBC.

Java 21, Maven, Quarkus 3. Стабильную версию платформы выбираем на этапе 1 и фиксируем в POM; примеры документации сверяем с ней. Расширения добавляем по мере надобности. PostgreSQL запускаем через Dev Services для dev/test, а на финальном этапе используем отдельную БД с постоянным хранилищем.

## Целевое приложение

Одна книга содержит `id: Long` (генерируется БД), `title: String`, `author: String`, `publicationYear: Integer`. Название и автор обязательны, не состоят из пробелов, длиной не более 200 символов; год обязателен и находится в диапазоне 1–2100 включительно. Одинаковые книги допустимы. Это учебные бизнес-правила, а не ограничения Quarkus.

Клиент передаёт три изменяемых поля; в DTO ответа дополнительно присутствует `id`. Для обновления используется полная замена этих трёх полей через PUT, без создания отсутствующей книги.

| Операция | Контракт к концу курса |
| --- | --- |
| `POST /books` | `201`, DTO созданной книги, `Location` на `/books/{id}` |
| `GET /books/{id}` | `200` и DTO либо `404` |
| `GET /books` | `200`, объект `{items, page, size, total}`; пустой результат — `items: []` |
| `PUT /books/{id}` | `200` и обновлённый DTO либо `404` |
| `DELETE /books/{id}` | `204` без тела либо `404`, в том числе при повторном удалении |

Все JSON-ответы имеют `Content-Type: application/json`. Ошибки входных данных — `400`. Единый формат предусмотренных ошибок 400/404 вводится на этапе 5: `{code, message, violations}`, где `violations` — массив объектов `{field, message}`, пустой для ошибок без конкретного поля. Текст сообщений свободный; стек исключения и SQL клиенту не возвращаются. Неизвестные ошибки не маскируются под 400 или 404.

Целевая структура: пакет `dev.ldv.book` с `BookResource`, `BookService`, `BookRepository`, `Book`, DTO запросов и ответов; общие HTTP-ошибки — в `dev.ldv.error`. REST отвечает за HTTP и DTO, сервис — за сценарии и границы транзакций, репозиторий — за запросы. Маппинг на старте ручной. Один класс не обязан иметь интерфейс.

## Этап 3. PostgreSQL, миграции и Repository

**Теория.** Panache сокращает шаблонный код поверх Hibernate ORM. В Repository-подходе сущность хранит состояние, а операции доступа к БД находятся в отдельном CDI-bean. Flyway версионирует схему; Dev Services помогает запускать зависимости для dev/test.

**Материалы:** [Panache — Repository pattern](https://quarkus.io/guides/hibernate-orm-panache/), [Dev Services для БД](https://quarkus.io/guides/databases-dev-services/), [Flyway](https://quarkus.io/guides/flyway/).

**ТЗ:**

- [ ] Проверить доступность Docker через `docker info`; если он недоступен, согласовать локальную PostgreSQL перед настройкой подключения.

Версии зависимостей согласуются через Quarkus BOM. Отдельная прямая зависимость `quarkus-hibernate-orm` не нужна, она входит в Panache.
- [ ] Настроить PostgreSQL Dev Services: указать `quarkus.datasource.db-kind`, задать явный версионный тег образа в `quarkus.datasource.devservices.image-name` (не `latest`) и записать выбранный тег в README. - [ ] Создать миграцию `src/main/resources/db/migration/V1__create_books.sql`: таблица `books`, первичный ключ и генерация id, NOT NULL, длины строк и ограничение года из контракта.

## Этап 4. Создание и чтение книг

**Материалы:** [Quarkus REST](https://quarkus.io/guides/rest/), [транзакции](https://quarkus.io/guides/transaction/), [HTTP-тесты](https://quarkus.io/guides/getting-started-testing/).

## Этап 5. Полный CRUD, валидация и ошибки

**Теория.** Bean Validation позволяет объявлять ограничения на DTO и проверять вход REST-метода через `@Valid`, как в Spring MVC. `ExceptionMapper` с `@Provider` переводит исключения в HTTP-ответы — по назначению близко к `@RestControllerAdvice` / `@ExceptionHandler`. Ошибки валидации входа REST и внутренних сервисных методов не обязательно получают одинаковые статусы автоматически. PUT полностью заменяет изменяемые поля существующей книги. Загруженная в транзакции JPA entity управляется Hibernate: изменения её полей сохраняются при flush благодаря dirty checking, отдельный аналог Spring Data `save` для неё не обязателен.

**Материалы:** [Hibernate Validator](https://quarkus.io/guides/validation/), [Quarkus REST — exception mapping](https://quarkus.io/guides/rest/#exception-mapping), [Jackson и встроенные обработчики](https://quarkus.io/guides/rest/#jackson-specific-features), [Panache — transactions](https://quarkus.io/guides/hibernate-orm-panache/#transactions).

**Уточнено и выдано 2026-09-28 после приёмки этапа 4.**

**ТЗ:**

- [ ] Заменить прямую зависимость `org.hibernate.validator:hibernate-validator` расширением `io.quarkus:quarkus-hibernate-validator`, версию получать из BOM.

- [ ] В `dev.ldv.error` ввести DTO ошибок и обработчики на основе Jakarta REST `ExceptionMapper` / `@Provider`. Формат предусмотренных ошибок API книг: `{code, message, violations}`, `violations` всегда массив `{field, message}`. Нарушения ограничений DTO — 400/`VALIDATION_ERROR`, с именами полей `title`, `author`, `publicationYear`. Ошибки JSON/типов и неверный path id — 400/`BAD_REQUEST`; отсутствующая книга — 404/`NOT_FOUND`. Для ошибок без конкретного поля допустим пустой массив. Тексты сообщений свободные, непустые, без SQL и стека исключения; порядок violations не фиксирован. Для JSON null всего DTO можно выбрать `BAD_REQUEST` либо `VALIDATION_ERROR`.
- [ ] Унифицировать 404 для GET/PUT/DELETE книг. Учесть, что возврат готового `RestResponse.notFound()` сам по себе не вызывает `ExceptionMapper`: обеспечить общее тело ошибки и на этом пути. Не преобразовывать все исключения подряд в 400 или 404; внутренние ошибки остаются серверными.
- [ ] Некорректный JSON (например, оборванный объект), неверный тип поля (например, объект вместо `title` или `"abc"` вместо года) и невалидный path id (`abc`, 0, отрицательный) дают 400 в общем формате; корректный положительный отсутствующий id — 404. Проверить id на GET/PUT/DELETE. Для теста PUT с плохим id использовать корректное тело, чтобы проверять именно id. Строгое запрещение всех преобразований скалярных типов Jackson сейчас не требуется.
- [ ] HTTP-тестами проверить POST и PUT: пустые/пробельные строки, null и пропущенные обязательные поля, длину 201, годы 0 и 2101. Проверить допустимые границы длины 200 и года 1/2100, JSON null всего DTO и ошибки JSON/типов. Для ошибок проверять статус, JSON content type, code, message и violations; для валидации — нужное поле без зависимости от порядка сообщений. Можно использовать параметризованные тесты.
- [ ] Проверить сценарий create → update → get → delete → get → повторный delete. Невалидный POST не создаёт запись; невалидный PUT оставляет прежние значения и количество книг, что подтверждается последующим GET/списком. Сохранить независимость тестов и существующие проверки этапов 1–4.
- [ ] Дополнить README примерами PUT/DELETE, форматами ошибок и кодами ответов. Прогнать `.\mvnw.cmd test` при доступном Docker.

**Подсказки:** сначала реализуй успешные PUT/DELETE, затем ограничения входа, затем общий формат ошибок. Ошибки чтения JSON и преобразования path-параметра могут возникать до входа в метод ресурса. В Quarkus REST есть встроенные обработчики, в том числе для Jackson `MismatchedInputException`; общий обработчик родительского типа не обязательно перекроет более специфичный. Проверяй фактический HTTP-ответ и сверяйся с документацией. Общий обработчик `Exception` с ответом 400 для всех случаев здесь не подходит.

**Приёмка:** тесты подтверждают весь CRUD и перечисленные ошибки; все предусмотренные ответы 400/404 API книг имеют общий JSON-формат. DELETE 204 не содержит тела. Невалидные запросы не изменяют БД; неизвестные внутренние исключения не превращаются в «книга не найдена» или ошибку входа. Внешние сообщения не содержат технических деталей исключений. Параметры списка по-прежнему остаются этапом 6.

## Этап 6. Фильтрация, пагинация и надёжность тестов

**Теория.** Пагинация ограничивает объём ответа, а стабильная сортировка делает страницы воспроизводимыми. HTTP-тест с `@QuarkusTest` проверяет взаимодействие слоёв; изоляцию данных нужно обеспечить отдельно. Транзакция тестового метода не означает автоматический откат операций отдельных HTTP-запросов.

**Материалы:** [Panache — paging и sorting](https://quarkus.io/guides/hibernate-orm-panache/), [тестирование Quarkus](https://quarkus.io/guides/getting-started-testing/).

**ТЗ:**

- [ ] Добавить параметры `page` (по умолчанию 0), `size` (по умолчанию 20, диапазон 1–100) и `author` к GET списка.
- [ ] Фильтр — точное совпадение автора без учёта регистра после удаления крайних пробелов в параметре; отсутствующий/пустой фильтр не ограничивает выборку.
- [ ] Применять фильтр, сортировку `id ASC` и пагинацию в БД. `total` — число книг после фильтра, до пагинации. Страница за пределами выборки возвращает пустой `items`.
- [ ] Нечисловые/отрицательные page и недопустимые size дают 400 в общем формате.
- [ ] Проверить несколько страниц, фильтр, пустой результат, неверные параметры и полный сценарий create → read → update → delete.
- [ ] Обеспечить независимые тестовые данные и очистку только тестовой БД. Тесты не зависят от порядка, существующих записей или конкретного первого id.

**Приёмка:** весь набор проходит при двух последовательных запусках, результаты не зависят от накопленных тестовых записей; фильтр и total согласованы.

## Этап 7. Документация API и запуск вне dev mode

**Теория.** OpenAPI описывает контракт API, Swagger UI позволяет его исследовать. Health endpoints сообщают о работоспособности и готовности приложения. Собранное JVM-приложение использует явные настройки окружения; Dev Services предназначены для dev/test.

**Материалы:** [OpenAPI и Swagger UI](https://quarkus.io/guides/openapi-swaggerui/), [SmallRye Health](https://quarkus.io/guides/smallrye-health/), [сборка и запуск](https://quarkus.io/guides/getting-started/#packaging-and-run-the-application).

**ТЗ:**

- [ ] Подключить `quarkus-smallrye-openapi` и `quarkus-smallrye-health`. Описать операции, DTO, параметры и ожидаемые ответы CRUD.
- [ ] Проверить `/q/openapi`, Swagger UI в dev mode, `/q/health/live` и `/q/health/ready`; readiness учитывает подключение к БД.
- [ ] Подготовить отдельную PostgreSQL с постоянным хранилищем, например через `compose.yaml`. Явно передавать JDBC URL, пользователя и пароль через переменные окружения; реальные секреты не хранить в Git.
- [ ] Выполнить `.\mvnw.cmd verify`, затем запустить стандартную fast-jar сборку: `java -jar target/quarkus-app/quarkus-run.jar` с настроенной БД.
- [ ] Проверить CRUD у собранного приложения и сохранение созданной книги после перезапуска приложения при той же БД.
- [ ] Завершить README: подготовка окружения, dev/test/packaged запуск, настройки БД, миграции, примеры CRUD и отличие readiness от liveness.

**Приёмка:** проверки Maven проходят, приложение работает вне dev mode, после его перезапуска данные доступны, инструкция позволяет повторить запуск. Для распространения fast-jar нужна вся папка `target/quarkus-app`.
