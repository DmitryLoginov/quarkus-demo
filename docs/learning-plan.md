# Quarkus: учебный CRUD с PostgreSQL

## Цель и порядок работы

Ты реализуешь REST API каталога книг и учишься объяснять его устройство через знакомые концепции Spring Boot. Ассистент выдаёт задания и делает ревью; исходный код и тесты пишешь ты. Ниже — маршрут и ТЗ, а не готовые решения. Текущий этап и история ревью находятся в [AGENTS.md](../AGENTS.md).

Каждая итерация: теория и чтение → реализация → проверка → ревью → исправления → контрольная точка. Дальние этапы задают ориентир; перед их началом наставник уточняет задание с учётом уже написанного кода.

## Выбор подхода

- **Hibernate ORM + Panache Repository — основной вариант.** Явный репозиторий позволит сравнить подход со Spring Data JPA, сохранив знакомые сущности и транзакции.
- Panache Active Record — компактнее, но операции хранения располагаются на самой сущности; сравним после освоения Repository.
- Hibernate Reactive — отдельная тема с другой моделью выполнения; для первого CRUD выбираем синхронные методы и JDBC.

Java 21, Maven, Quarkus 3. Стабильную версию платформы выбираем на этапе 1 и фиксируем в POM; примеры документации сверяем с ней. Расширения добавляем по мере надобности. PostgreSQL запускаем через Dev Services для dev/test, а на финальном этапе используем отдельную БД с постоянным хранилищем.

## Целевое приложение

Одна книга содержит `id: Long` (генерируется БД), `title: String`, `author: String`, `publicationYear: Integer`. Название и автор обязательны, не состоят из пробелов, длиной не более 200 символов; год обязателен и находится в диапазоне 1–2100 включительно. Одинаковые книги допустимы. Это учебные бизнес-правила, а не ограничения Quarkus.

Клиент передаёт три изменяемых поля; в DTO ответа дополнительно присутствует `id`. Для обновления используется полная замена этих трёх полей через PUT, без создания отсутствующей книги.

| Операция | Контракт к концу курса |
| --- | --- |
| `POST /books` | `201`, DTO созданной книги, `Location` на `/books/{id}` |
| `GET /books/{id}` | `200` и DTO либо `404` |
| `GET /books` | `200`, объект `{items, page, size, total}`; пустой результат — `items: []` |
| `PUT /books/{id}` | `200` и обновлённый DTO либо `404` |
| `DELETE /books/{id}` | `204` без тела либо `404`, в том числе при повторном удалении |

Все JSON-ответы имеют `Content-Type: application/json`. Ошибки входных данных — `400`. Единый формат предусмотренных ошибок 400/404 вводится на этапе 5: `{code, message, violations}`, где `violations` — массив объектов `{field, message}`, пустой для ошибок без конкретного поля. Текст сообщений свободный; стек исключения и SQL клиенту не возвращаются. Неизвестные ошибки не маскируются под 400 или 404.

Целевая структура: пакет `dev.ldv.book` с `BookResource`, `BookService`, `BookRepository`, `Book`, DTO запросов и ответов; общие HTTP-ошибки — в `dev.ldv.error`. REST отвечает за HTTP и DTO, сервис — за сценарии и границы транзакций, репозиторий — за запросы. Маппинг на старте ручной. Один класс не обязан иметь интерфейс.

## Этап 3. PostgreSQL, миграции и Repository

**Теория.** Panache сокращает шаблонный код поверх Hibernate ORM. В Repository-подходе сущность хранит состояние, а операции доступа к БД находятся в отдельном CDI-bean. Flyway версионирует схему; Dev Services помогает запускать зависимости для dev/test.

**Материалы:** [Panache — Repository pattern](https://quarkus.io/guides/hibernate-orm-panache/), [Dev Services для БД](https://quarkus.io/guides/databases-dev-services/), [Flyway](https://quarkus.io/guides/flyway/).

**ТЗ:**

- [ ] Проверить доступность Docker через `docker info`; если он недоступен, согласовать локальную PostgreSQL перед настройкой подключения.
- [ ] Подключить `io.quarkus:quarkus-hibernate-orm-panache`, `io.quarkus:quarkus-jdbc-postgresql`, `io.quarkus:quarkus-flyway` и `org.flywaydb:flyway-database-postgresql`. Версии зависимостей согласуются через Quarkus BOM. Отдельная прямая зависимость `quarkus-hibernate-orm` не нужна, она входит в Panache.
- [ ] Настроить PostgreSQL Dev Services: указать `quarkus.datasource.db-kind`, задать явный версионный тег образа в `quarkus.datasource.devservices.image-name` (не `latest`) и записать выбранный тег в README. Для dev/test не задавать JDBC URL к внешней БД: подключение выдаёт Dev Services. Тесты используют отдельную учебную БД.
- [ ] Создать миграцию `src/main/resources/db/migration/V1__create_books.sql`: таблица `books`, первичный ключ и генерация id, NOT NULL, длины строк и ограничение года из контракта.
- [ ] Flyway применяет миграции при запуске (`quarkus.flyway.migrate-at-start`); Hibernate проверяет схему через `quarkus.hibernate-orm.schema-management.strategy=validate`. Автоматическое создание/обновление схемы Hibernate отключено. Согласовать стратегию генерации id между entity и SQL.
- [ ] Создать `src/main/java/dev/ldv/book/Book.java`: обычная JPA entity, таблица `books`, поля `id: Long`, `title: String`, `author: String`, `publicationYear: Integer` по общему контракту. Колонку года явно назвать `publication_year`. Можно выбрать IDENTITY либо SEQUENCE, но настройки Java и миграция должны соответствовать друг другу.
- [ ] Создать `src/main/java/dev/ldv/book/BookRepository.java`: CDI-bean с `@ApplicationScoped`, реализующий `PanacheRepository<Book>`. HTTP-операции с книгами появятся на этапе 4.
- [ ] Добавить `src/test/java/dev/ldv/book/BookRepositoryTest.java` с `@QuarkusTest`: внедрить репозиторий и проверить сохранение/чтение через настоящую PostgreSQL. Для отката изменений этого тестового метода использовать `io.quarkus.test.TestTransaction`.
- [ ] В тесте создать корректную книгу, сохранить, выполнить flush и clear persistence context, затем прочитать по полученному id и проверить все поля. Не предполагать, что первый id равен 1. Существующий HTTP-тест `/api/info` также должен проходить.
- [ ] Дополнить README: выбранный образ PostgreSQL, запуск Docker/Dev Services, ответственность Flyway и Hibernate, проверка миграции. Заодно закрыть небольшое дополнение N2 этапа 2: указать Resource → Service → Config и `book-catalog` / `book-catalog-test`.

**Приёмка:** `.\mvnw.cmd test` выполняет HTTP-тест и тест репозитория без ошибок. Тест сохраняет книгу, получает сгенерированный id и читает поля из БД после flush/clear; тестовые изменения откатываются. На чистой БД миграция создаёт схему, Hibernate validate проходит. Повторный вызов миграции на той же БД не применяет V1 повторно: подтвердить журналом Flyway или его schema history (это можно проверить в одной dev-сессии; новый контейнер может иметь новую БД). После применения миграцию не переписываем: изменения схемы — новая версия.

**Материалы для проверки:** [Hibernate schema management](https://quarkus.io/guides/hibernate-orm/#hibernate-orm-in-development-mode), [тестовые транзакции](https://quarkus.io/guides/getting-started-testing/#tests-and-transactions). `validate` проверяет соответствие маппинга схеме, но не заменяет проверку всех бизнес-ограничений SQL.

## Этап 4. Создание и чтение книг

**Теория.** HTTP-контракт отделяется от схемы хранения через DTO. Сервис объединяет действия сценария; изменения в БД выполняются в транзакции с `jakarta.transaction.Transactional`. В Panache Repository методы доступа реализуются иначе, чем генерируемые методы интерфейсов Spring Data.

**Материалы:** [Quarkus REST](https://quarkus.io/guides/rest/), [транзакции](https://quarkus.io/guides/transaction/).

**ТЗ:**

- [ ] Создать `BookService`, `BookResource`, DTO создания и ответа, DTO страницы `{items, page, size, total}`.
- [ ] Реализовать POST, GET по id и GET списка из целевого контракта.
- [ ] Пока список возвращает первые 20 книг по `id ASC`, `page=0`, `size=20`, `total` равен количеству всех книг. Параметры и фильтр добавим на этапе 6.
- [ ] Открывать транзакцию записи на сервисном методе создания. JPA entity не возвращать непосредственно клиенту.
- [ ] Проверить через HTTP создание → чтение по id → наличие в списке; проверить `Location`, неизвестный id и пустую БД.

**Приёмка:** контракты успешных ответов соблюдены, неизвестный id даёт 404, данные действительно попадают в PostgreSQL. На этом этапе формат тела 404 ещё свободный; тесты используют корректные входные данные.

## Этап 5. Полный CRUD, валидация и ошибки

**Теория.** Bean Validation позволяет объявлять ограничения на DTO и проверять вход REST-метода через `@Valid`. `ExceptionMapper` переводит исключения в HTTP-ответы — по назначению близко к обработчикам ошибок Spring. Ошибки валидации входа REST и внутренних сервисных методов не обязательно получают одинаковые статусы автоматически.

**Материалы:** [Hibernate Validator](https://quarkus.io/guides/validation/), [Quarkus REST — exception mapping](https://quarkus.io/guides/rest/#exception-mapping).

**ТЗ:**

- [ ] Подключить `quarkus-hibernate-validator`; применить ограничения из контракта к DTO создания и полной замены.
- [ ] Реализовать PUT и DELETE с транзакциями на сервисных методах.
- [ ] Ввести общий формат ошибок 400/404: `code=VALIDATION_ERROR`, `BAD_REQUEST` либо `NOT_FOUND` в зависимости от причины.
- [ ] Проверять пустые/пробельные строки, null и пропущенные обязательные поля, длину 201, годы 0 и 2101; границы 1 и 2100 допустимы.
- [ ] Некорректный JSON, неверный тип поля и невалидный path id (`abc`, 0, отрицательный) дают 400 в общем формате; корректный положительный отсутствующий id — 404.
- [ ] Проверить обновление без изменения id, удаление и повторное удаление. Невалидный запрос не меняет данные в БД.

**Приёмка:** тесты подтверждают весь CRUD и перечисленные ошибки; неизвестные внутренние исключения не превращаются в «книга не найдена». Внешние сообщения не содержат технических деталей исключений.

## Этап 6. Фильтрация, пагинация и надёжность тестов

**Теория.** Пагинация ограничивает объём ответа, а стабильная сортировка делает страницы воспроизводимыми. HTTP-тест с `@QuarkusTest` проверяет взаимодействие слоёв; изоляцию данных нужно обеспечить отдельно. Транзакция тестового метода не означает автоматический откат операций отдельных HTTP-запросов.

**Материалы:** [Panache — paging и sorting](https://quarkus.io/guides/hibernate-orm-panache/), [тестирование Quarkus](https://quarkus.io/guides/getting-started-testing/).

**ТЗ:**

- [ ] Добавить параметры `page` (по умолчанию 0), `size` (по умолчанию 20, диапазон 1–100) и `author` к GET списка.
- [ ] Фильтр — точное совпадение автора без учёта регистра после удаления крайних пробелов в параметре; отсутствующий/пустой фильтр не ограничивает выборку.
- [ ] Применять фильтр, сортировку `id ASC` и пагинацию в БД. `total` — число книг после фильтра, до пагинации. Страница за пределами выборки возвращает пустой `items`.
- [ ] Нечисловые/отрицательные page и недопустимые size дают 400 в общем формате.
- [ ] Проверить несколько страниц, фильтр, пустой результат, неверные параметры и полный сценарий create → read → update → delete.
- [ ] Обеспечить независимые тестовые данные и очистку только тестовой БД. Тесты не зависят от порядка, существующих записей или конкретного первого id.

**Приёмка:** весь набор проходит при двух последовательных запусках, результаты не зависят от накопленных тестовых записей; фильтр и total согласованы.
